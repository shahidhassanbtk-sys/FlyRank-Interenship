Abstract

Content that ranks in Google search quietly decays — rankings slip and clicks drop before a review team notices, and today FlyRank's product flags that decay with a hand-written rule (a health score and threshold-based tags). This project asks whether a trained model, using the same available search, content, and performance signals, can prioritize FlyRank's page-review queue better than that fixed rule. Working on a pseudonymized slice of FlyRank's real search-performance warehouse, I built page-level features, trained a model under a client-aware validation split, and compared it against the hand-written baseline on identical held-out clients — with the result reported honestly below, whichever way it fell. The output is a ranked, human-reviewed action queue intended as decision-support for FlyRank's content-review workflow, not an autonomous publishing decision.

1. Introduction — the FlyRank problem

FlyRank runs content as infrastructure: it researches, writes, and publishes content straight into a client's website, then watches search data and optimizes — the full cycle, run largely by algorithms rather than people doing it by hand. The valuable decision FlyRank's team faces daily is not whether a page needs attention, but which one, out of thousands, should a human look at first?

FlyRank's product already answers this today with a hand-written rule: a health score and quick-win tags built from if-this-then-that thresholds someone chose by hand. Those rules work and run in production — but they run out where signals get numerous, tangled, and shifting, and no trained model has replaced them yet. That gap, "beat the rule" on real data with honest validation, is exactly where this capstone sits: a ranking problem on messy, real search data, solved in a way a human reviewer can trust and act on.

2. Data

This analysis uses the FlyRank internship warehouse dataset (Google Search Console + Google Analytics data, synced to BigQuery and shipped to interns as a pseudonymized, public-safe release), accessed through the FlyRank / Hugging Face warehouse and the starter repository. No private or personally identifying data was added.

The relevant signals include: search and keyword performance, impressions and clicks, page/content information, and other performance-related features available at the time a page would be reviewed.

Excluded: private or personally identifying information; data not required for the research question; records with missing or unusable values that can't be used reliably; data outside the analysis window provided.

3. Methodology

Label

A page is a positive example when its impressions have declined compared with the previous measurement period. Zero-impression pages are excluded from this pipeline — a decline can't be measured reliably for a page with no impressions to begin with; that's a separate indexing/discoverability problem.

Baseline

The baseline is FlyRank's existing hand-written rule (the product's own health-score flags), evaluated on exactly the same held-out rows as the model — never used as a model input, since that would be circular (the rule already encodes a decision, not a raw signal).

Validation design

A client-aware holdout split: pages belonging to one client stay together, so no client appears in both training and test. The model trains only on training clients and is scored on clients it has never seen. The hand-written rule runs on that identical held-out set.

Leakage checks

  • No feature drawn from the target/future measurement period
  • The target itself excluded from the feature set
  • Train/test separated by client, not by row
  • CTR excluded where it would leak the outcome (it's derived from clicks and impressions)
  • Any preprocessing fit on training data only

5. Limitations

This work cannot claim that:

  • results will hold for future data or different clients
  • the model will always outperform the hand-written baseline
  • a high model score proves a page needs a specific action, or proves the cause of a change
  • results generalize to sites or datasets outside this project's type
  • the model can replace human review and decision-making

Zero-impression pages are handled by a separate pipeline, not this one.

6. Ranked recommendations

  1. Review the highest-scoring pages first — start at the top of the ranked queue.
  2. Investigate the supporting signals — check the search, content, and performance data behind the score.
  3. Prioritize pages with clear evidence — the score is a starting point, not proof.
  4. Route zero-impression pages separately — into the indexing/discoverability workflow, not content refresh.
  5. Human review before any action — a reviewer inspects the page and evidence before anything changes.
